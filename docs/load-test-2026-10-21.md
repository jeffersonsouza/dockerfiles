# PHP/Nginx load test — 2026-10-21

Reference date: America/Sao_Paulo. Local ARM64 Docker runtime; one container at a time, limited to 1 vCPU, with swap disabled. The load generator ran on the Docker host. PHP versions: 8.2.35, 8.3.36, 8.4.27 and 8.5.12.

## Result

All eight profiles and forty ApacheBench scenarios passed: **956,083 completed requests, zero HTTP/client errors, zero OOM events and zero service restarts**. Containers remained healthy and shut down with exit code 0. An additional HTTP/1.1 run completed 17,048 requests successfully, including a sustained memory-heavy stage.

## Method

- 256 MiB: one FPM worker. 512 MiB: two FPM workers. OPcache: 64 MiB; PHP memory limit: 128 MiB per request.
- Five 10-second scenarios per profile: dynamic JSON index with 1, 8 and 32 concurrent clients; a no-store endpoint with 32 clients allocating 96 MiB per request, executing 10,000 PBKDF2 iterations and sleeping 20 ms; a primed, explicitly public cached response with 32 clients.
- ApacheBench used `-k -l -r -t 10 -n 1000000`. The actual keep-alive count was zero: these measurements use HTTP/1.0 with new connections. `-l` allows the dynamic response length to vary. JSON content, timestamp changes, cache headers and health were checked separately.
- The memory peak comes from cgroup `memory.peak` across all scenarios, including the 96 MiB allocations. CPU throttling was observed under the intentional 1-vCPU cap. No memory limit was reached.

The runner is `.github/scripts/load-test-php.py`. See the [ApacheBench documentation](https://httpd.apache.org/docs/2.4/programs/ab.html) for its options and load-generator limitations.

## Issue found and corrected

The initial run had no functional errors but exposed avoidable latency: `fastcgi_cache_lock on` serialized requests to endpoints whose no-store responses never populated the cache. Nginx logs showed approximately 5 seconds total request time while PHP upstream work took about 44 ms. Disabling the lock in the generic PHP location removed that wait; public caching still passed privacy, TTL, Vary and purge checks.

Nginx documents the cache-fill lock and its default five-second timeout in the [FastCGI module reference](https://nginx.org/en/docs/http/ngx_http_fastcgi_module.html#fastcgi_cache_lock). The cause was confirmed by an isolated configuration change and a concurrency regression that failed on the old image and passed on the corrected images.

## Scope and reproducibility

The compact reference shipped in `new/php/benchmark.json` contains only the date, architecture and eight profile results shown on the welcome page. HTML guidance and the recorded reference are processed after the JSON response returns, so they do not change the measured JSON endpoint. Final images were rebuilt with these presentation additions and checked separately.

These are synthetic infrastructure measurements, not a production capacity guarantee. They exclude database, Redis, TLS, external network latency and application workloads. The host also ran unrelated containers, so small differences between PHP versions are not evidence of a ranking. No local AMD64 load test was performed; the workflows are configured to build and smoke-test AMD64 and ARM64 before publishing. CI itself has not run for this local branch.

To repeat the ApacheBench matrix, build each PHP image using the `new/` context and run the load-test script once for `--memory 256 --children 1` and once for `--memory 512 --children 2`, always using a fresh output directory. Preserve each `summary.json`, raw stage output and container log outside the image. The HTTP/1.1 cross-check used curl 8.21 with 5,000 index transfers, 10,000 primed-cache transfers and 2,048 transfers to the same heavy fixture.
