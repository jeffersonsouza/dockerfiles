# PHP/Nginx verification after APK migration — 2026-10-22

PHP 8.3.36, 8.4.27 and 8.5.12 now use Alpine 3.24 packages, including PHP extensions. PHP 8.2.35 keeps the official precompiled PHP core with compatible additional extensions compiled separately and native libraries installed by APK. Every image keeps this repository's customized Nginx configuration and modules.

## Compatibility and security checks

- All three APK images passed the full smoke/security suite in ARM64 and AMD64 at 256 MiB/one worker and 512 MiB/two workers. AMD64 was emulated locally; CI uses a native runner. PHP 8.2 passed both memory profiles in native ARM64.
- All previously loaded standard modules were retained, including `posix`, `sqlite3` and `xmlreader`. Module inventories were compared against the previous runtime.
- Version and extension checks, APK provenance, Nginx/FPM startup, fresh HTML/JSON diagnostics, cache privacy, Vary, authentication/cookies, purge ACLs, protected files, upload limits, compression, session persistence, error logging, OPcache, concurrent 96 MiB allocations and graceful shutdown passed.
- INI and FPM pool bind mounts at the common `/usr/local/etc/` paths were verified in all four series. APK images also keep their native `/etc/php83`, `/etc/php84` and `/etc/php85` configuration paths.
- The warm 8.2 log confirmed that the extension compilation was cached and the final APK installation was executed again. Docker save/load and OCI export preserved the image configuration hash and healthcheck; publication checks use the config blob, since Docker/containerd image IDs may identify different objects.
- The first AMD64 test attempt encountered a full Docker virtual disk. Only task-owned intermediate image/cache records were removed; the full AMD64 suite then passed. Other projects' containers and volumes were not modified.

## Load test

Forty scenarios across eight profiles completed **863,919 requests with zero HTTP/client errors, zero OOM events and zero service restarts**. Each temporary container had 1 vCPU, no swap, OPcache 64 MiB and PHP memory limit 128 MiB per request. All containers shut down cleanly.

Each profile ran five 10-second ApacheBench stages: uncached JSON index at 1, 8 and 32 clients; a no-store route allocating 96 MiB, executing 10,000 PBKDF2 iterations and sleeping 20 ms at 32 clients; and an explicitly public, primed FastCGI cache response at 32 clients. ApacheBench used HTTP/1.0 without effective connection reuse. Content, changing timestamps and cache headers were checked separately.

## Limits and reproducibility

The load generator ran on the same ARM64 Docker host, alongside unrelated containers. These synthetic measurements exclude databases, Redis workloads, TLS and the real application. They are a reference, not a production capacity guarantee or a ranking of PHP versions. No AMD64 load test or new sustained HTTP/1.1 run was performed in this migration.

Build the image and run `.github/scripts/load-test-php.py` with `--memory 256 --children 1` and `--memory 512 --children 2`, using a fresh output directory for each. Raw stage outputs, container logs and summaries were kept locally outside Git. The compact sanitized reference is saved in `new/php/benchmark.json` and shown in the welcome page.

The [2026-10-21 report](load-test-2026-10-21.md) describes the earlier all-official-runtime build and the cache-lock fix. The current measurements above supersede its capacity reference for the APK images.
